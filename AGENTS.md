# Implementation instructions

Read SPEC.md, STORY.md, ART.md, PLAN.md, and STATUS.md before implementing. Work in this project's dedicated checkout. These documents specify a complete first episode; do not turn it into a landing page or a generic choice-button demo.

- The user delegates routine story, art, and engineering decisions. Preserve the agreed concept and scope; record material adjustments in STATUS.md.
- Work through implementation, verification, public GitHub delivery, and public deployment. Keep progressing without milestone approval prompts.
- Use subagents for bounded independent work where useful. Respect applicable Sites ownership rules: the site owner handles project source, integration, and publishing; delegate asset/research assignments as permitted. Give explicit ownership and completion criteria; avoid concurrent edits to the same files.
- Public GitHub visibility and public game access are explicitly requested. Verify the authenticated owner and permissions before publishing. Never overwrite an unrelated repository or publish secrets.
- No extra spending, paid assets, paid API usage, or paid-plan activation is authorized. Do not invent licenses or credentials.
- Use applicable Sites, hosting, GitHub, and image-generation skills when performing those operations. Follow actual current tool capabilities rather than assuming this planning environment's configuration persists.
- Keep the game client-side and saves explicitly browser-local. No player login or live AI dependency.
- Provide checkpoint commits and update STATUS.md after meaningful milestones. Record blockers and continue work that does not depend on them.
- Validate story state and real player workflows. Do not weaken tests, remove choices, replace art with placeholders, or mark criteria passed merely to finish.
- Take screenshots and inspect the actual game at representative dimensions. Treat text overflow, illegible choice states, and inconsistent character art as defects.
- An early visual preview is welcome, but do not require a response before continuing. Ask only when access, significant scope changes, or unresolved product decisions truly block work.
- Final report: public repo URL, public game URL, verified checks, actual pacing evidence, and known limitations. If blocked, distinguish implemented work from inaccessible publishing or unverified quality.
